# GPT-6 Luna: 不確定性・課題種別・根拠の比較

## 結論

**正しい値、出力形式、確定してよいだけの根拠は、別々に測る必要がある。**
今回のLunaでは、文章による型指定を追加した条件が悪化した。根拠の指示だけを
加えた条件は15/15だったが、直った1件は引用ではなくフラグ形式の違いだった。
「型を明示すれば改善する」「根拠の指示で推論が改善した」とは結論しない。

前回のMistralと同じ入力による比較では、空記録の配送問題で同じフラグ脱落が
再現した。一方、Mistralの改訂版で残った2件の失敗はLunaでは再現しなかった。
これは限定された校正結果であり、モデル一般の優劣やscratchpadの有効性ではない。

## 実施範囲

- 正式API名 `gpt-6-luna`。指定の呼び名 `gpt-luna-6` との対応を実行前に説明し、
  既存キーの再利用について明示的な承諾を得た。
- 前回の入力・system文字列をそのまま使う24回と、新しい10課題・15提示条件を
  4群で比べる60回。計84回を一度ずつ実行した。
- Responses / high reasoning / JSON-object / max_output_tokens4096 / timeout90s /
  store=false。全群で同じLuna設定。追加修復、再試行、結果を見た有料再調整は0回。
- 全84応答が完了し、モデル・要求パラメータも一致。通信失敗、出力上限、
  usage欠落は0件。生応答を残し、旧記録・旧採点は変更していない。
- [事前プロトコル](luna-uncertainty-v3-protocol.md)と旧12/12ゲートは維持した。
  全件が契約校正であり、失敗した旧pilotの再開でも新しい検索pilotでもない。

## 同一入力でのモデル間比較

| 入力群 | Mistral 値 | Luna 値 | Mistral 厳密通過 | Luna 厳密通過 |
|---|---:|---:|---:|---:|
| v2の12入力 | 12/12 | 12/12 | 11/12 | 11/12 |
| v2.1の12入力 | 12/12 | 12/12 | 10/12 | 12/12 |

共通の失敗はv2の空記録・配送問題だった。どちらも安全に保留したが、必要な
`urgent` / `hold` の `unobserved` を省略した。

```json
{"status":"unknown","value":null,"evidence":[],"flags":{}}
```

これは値の捏造でも、未確認を無効にする誤りでもない。**内容が不明なことと、
その課題で必要なフィールドの形が失われることが結び付いてしまった**事例である。

v2.1では、Mistralだけにあった「正しいFAST値なのに例外規則の引用がない」件と、
「空記録のjoinへ配送フラグが混入する」件をLunaは通過した。したがって、その
2件をこの入力におけるモデル共通の失敗とは呼べない。

プロンプトは同じだが、provider、adapter、生成日、native sampling設定は異なる。
Mistralのtemperature0/top_p1/seedに対し、Lunaのhighではそれらを送っていない。
同じhighという名前でも計算量は同一ではなく、重みだけの因果比較にはならない。

## 新ケースでの4条件

全条件で同じ公開記録、同じ正解規則、同じ出力上限を使った。課題種別の条件は
ラベルと課題別JSON Schemaを**文章として**入力に付ける方式で、provider側の
strict schema強制ではない。根拠の条件は、分岐ごとに必要な記録の種類を列挙した。

| 条件 | 値が正しい | フラグ忠実 | 要求ID網羅 | 厳密通過 |
|---|---:|---:|---:|---:|
| 従来 v2.1 (`generic`) | 15/15 | 14/15 | 15/15 | 14/15 |
| 課題種別・型だけ (`task-kind`) | 14/15 | 10/15 | 15/15 | 9/15 |
| 分岐別の根拠指示だけ (`proof`) | 15/15 | 15/15 | 15/15 | 15/15 |
| 両方 (`task-kind+proof`) | 15/15 | 14/15 | 15/15 | 14/15 |

15条件は10課題の投影であり、15個の独立サンプルではない。空記録は配送・決定・
joinの各種類に置き、規則の欠落と参照鎖の途中切れも残した。結果による除外はない。

同じ提示条件の対比較では、型だけの追加で従来の通過5件が失敗へ変わり、改善は
0件だった。根拠の指示だけでは1件が通過へ変わった。両方は型だけに比べ5件を
回復したが、従来条件と同じ1件の空記録・配送で失敗した。

Luna全84回では、JSONとしては84/84、値は83/84、フラグは76/84、厳密通過は75/84。
失敗はフラグ形状8件と、契約上確定できない値の確定1件だった。引用IDの欠落、
不可視ID、無関係ID、未確認から無効への書き換えはこの校正では観測されなかった。

ただし「要求ID網羅」は、その提示条件の参照判定が要求したIDの包含検査であり、
任意の出力値を証明する保証ではない。部分記録をすべて引用していても、それを
根拠に具体値を確定してよいとは限らない。次の失敗がその例である。

## 何が壊れたか

### 型の文章指定後も、型そのものが守られない

課題種別・型だけの条件では、根拠が揃った既知のHOLD回答でも配送フラグを落とした。

```json
{"status":"known","value":"HOLDP62ac9","evidence":["m005","m009"],"flags":{}}
```

値も引用も正しい。失敗は課題に必要な形の維持だった。空記録だけの問題ではない。
型をモデルに「説明する」ことと、呼び出し側が型を「保証する」ことは同一ではない。
今回の9/15を、実際のAPIによる構造化出力の成績と解釈してはいけない。

### 当たった具体値と、確定を許される値も異なる

例外規則を隠し、policyとrequestだけを提示した対照で、型だけの条件は次を返した。

```json
{"status":"known","value":"FASTPfb33e","evidence":["m001","m009"],
 "flags":{"urgent":"enabled","hold":"disabled"}}
```

公開された2記録はすべて引用され、フラグも正しい。しかし、この実験の保守的な
契約ではFAST/BASEには例外規則も提示されている必要があり、期待値は `unknown` /
nullだった。全記録を知る参照世界では同じFASTになるが、その隠れた記録を回答者が
使うことはできない。**世界の答えが当たったことは、提示根拠からの確定許可ではない。**

これは凍結した保留規則への違反であり、自然言語一般で唯一可能な推論規則だとは
主張しない。「欠落する規則をどう扱うか」は設計方針であり、評価にも明記が必要だ。
従来、根拠指示だけ、両方の3条件は同じ部分記録で保留できた。

## 共通項の抽象化

### 1. 内容の不確定性と、出力の型を分ける

観測: 両モデルで空記録の配送フラグが脱落した。Lunaの型だけの条件では既知の
値でも脱落した。したがって、未確定値のnull化だけでは出力契約を維持できない。

設計提案: 課題種別と必須フィールドは呼び出し側で決め、モデルにその選択まで
委ねない。内容はunknown/unobservedを許すが、必要なフィールド自体は消さない。
今回実装した課題別schema選択と既存validatorは足場になるが、API側の型強制は
まだ検証していない。現行schemaもprompt用で、API対応subsetとしては未確認である。

### 2. 答え、利用可能な根拠、提示した根拠を分ける

Mistralの「根拠は揃っているが引用が不足」と、Lunaの「部分記録しかないのに
具体値を確定」は異なる失敗である。前者は提示した証明、後者は確定の許可に穴が
ある。どちらも値だけの正解率では見落とす。全記録の答えを知る評価者も、回答者に
見えていない記録を暗黙に足して合格させてはいけない。

### 3. 指示の追加は、局所的・単調な改善ではない

観測: 型だけ9/15、根拠だけ15/15、両方14/15。根拠条件の1件の改善は引用漏れの
修正ではなくフラグ形式の差だった。目的として付けた指示名と、変わった出力の
部位は一致するとは限らない。

仮説: 指示の優先順位、語彙の対応、長さが影響した可能性がある。今回の種別名は
`scoped-exception`、元systemの呼び方は `routing` で、両者の対応は明示していない。
schemaもuser入力側、条件付きの一般規則はsystem側にある。ただし、これらを
個別には比較していないので、どれが原因かは断定しない。単一応答の揺らぎも残る。

### 4. 現段階の磨きどころは、文章の追加より責務の分離

次の候補は、種別語彙を統一し、出力形の固定・値の不確定性・証明の検証を分ける
設計である。値を出した後に隠れた正解や引用を自動挿入して整える方法は採らない。
不確定な値に根拠がある状態も、そのまま検査できるようにする。

根拠だけ15/15は有望な校正結果だが、Lunaでは元々引用欠落が0件で、改善は1提示
条件だけである。通常チャットへ採用したり、一般的な推論向上と呼ぶ段階ではない。
別の新ケース、複数回の応答、より厳しい根拠連鎖で確認すべきであり、今回は追加の
有料実験・独立確認・検索pilotを行っていない。
